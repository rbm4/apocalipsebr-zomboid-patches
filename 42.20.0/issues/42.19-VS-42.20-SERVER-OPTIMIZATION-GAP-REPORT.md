# 42.19.0 vs 42.20.0 Server-Side Optimization Gap Report

## Purpose

This report exists to plan the 42.20.0 dedicated-server optimization work. It answers
three questions:

1. What server-side optimizations already shipped in `42.19.0/src` and what problems did
   they solve or introduce?
2. What is actually present in `42.20.0/src` today, and how does it compare?
3. Given the operator constraints (70-slot server, currently healthy, no telemetry yet,
   avoid deep structural change before telemetry exists), what is the safe, prioritized
   order of work for 42.20.0 - starting with a minimal telemetry pack (players, zombies,
   server tick rate, packet queue depth) and then the lowest-risk "easy win" fixes?

Scope is server-side only. Anything gated by `!GameServer.server` / `isClient()`-style
branches, or that only affects the local client/singleplayer path, is out of scope.

---

## 1. Current state of `42.20.0/src`

As of this report, `42.20.0/src` contains only **3 patched files**, all decompiled-vanilla
plus a small targeted diff (verified with `git diff --no-index` against
`42.20.0/decompiled`):

### 1.1 `zombie/MovingObjectUpdateScheduler.java` - server simulation tiering (ported)

Real diff vs vanilla 42.20 decompiled:

- `getUpdateSchedulerSimulationLevelForObject()` now branches on `GameServer.server` first.
  On the server, vehicles and animals get dedicated simulation-level logic instead of
  vanilla's default (`isEnabled && !GameServer.server` short-circuit, which effectively
  gave the server the vanilla per-object minimum simulation level for everything).
- `getServerSimulationLevelForVehicle()`: `FULL` if driven, mechanic UI open, needs parts
  update, engine not idle, alarm/siren/lightbar active, towing/towed, not at rest, has
  animals aboard, or has any seated character. Otherwise `SIXTEENTH`.
- `getServerSimulationLevelForAnimal()`: `HALF` if held/lured/attacking/fighting/thumping/
  alerted/in a vehicle/on a hook. Otherwise `SIXTEENTH`.

This is a **direct, faithful port** of the concept in
`42.19.0/issues/FIRST-RELEASE-SERVER-OPTIMIZATIONS-OVERVIEW.md` section 4-5 (animal/vehicle
tiering), though the exact bucket values differ slightly from 42.19's documented baseline
(42.19 docs describe animal baseline as `HALF`/inactive `SIXTEENTH`; 42.20's src uses
`HALF` only when "active" and `SIXTEENTH` as the idle baseline - functionally the same
shape, just inverted default vs. exception). No telemetry hook is wired to this in
42.20.0 yet (42.19.0 counted this via `movingAnimalBuckets`/`movingBucketZombies` etc. in
`ApocBRServerTelemetry`).

**Risk:** low. This is a pure branch-classification change with no threading model change.

### 1.2 `zombie/inventory/ItemContainer.java` - capacity increases (NOT a performance patch)

Real diff vs vanilla 42.20 decompiled:

- `getCapacity()`: vehicle-part container cap raised from 1000 -> 3000; item-in-item cap
  raised from 50 -> 100; default cap raised from 100 -> 150.
- `setCapacity()` warning thresholds adjusted to match.

This is a **gameplay/balance change** (bigger containers), not a server-optimization
patch. It has no analogue in `42.19.0/src` (42.19's `ItemContainer.java` was confirmed
byte-identical to decompiled per `PATCHED-SOURCE-DIFF-AUDIT-2026-07.md`). Flagging this
explicitly so it is not mistaken for ported performance work when reconciling the two
trees. It is arguably server-relevant only in that bigger containers mean fewer container
objects/tiles are needed to store the same loot, which is a second-order, unmeasured effect.

**Risk:** none from a stability standpoint; it is a design decision independent of this report's optimization scope.

### 1.3 `zombie/pathfind/PolygonalMap2.java` - `supercover()` hardening (ported)

Real diff vs vanilla 42.20 decompiled:

- `MAX_SUPERCOVER_CELLS = 10000` safety cap added.
- `supercover()` rejects non-finite (`NaN`/`Infinite`) input coordinates immediately.
- Iteration is now capped at `MAX_SUPERCOVER_CELLS` (defensive `return` instead of an
  unbounded loop).
- Duplicate-point detection changed from `ArrayList.contains()` (O(n) per point, O(n^2)
  overall) to an `O(1)` `HashSet<Long>` keyed by packed `(x,y)` coordinates.
- One unrelated decompiler artifact cleanup: `(boolean)adjusted` -> `adjusted != 0`.

This matches exactly the "Pathfind / collision math" row of
`PATCHED-SOURCE-DIFF-AUDIT-2026-07.md`'s per-subsystem table (infinite-loop guard +
`HashSet` dedup instead of `ArrayList.contains`, NaN/Infinite input rejection). It is a
faithful, self-contained port with no dependency on any other patched file.

**Risk:** very low. Pure algorithmic hardening of a self-contained method; behavior is
identical for all previously-valid inputs, and only changes behavior for inputs that would
previously have hung or thrown.

### Summary: what 42.20.0 has vs. what 42.19.0 shipped

| 42.19.0 subsystem area | Ported to 42.20.0? |
|---|---|
| Vehicle/animal server simulation tiering (`MovingObjectUpdateScheduler`) | **Yes** |
| Pathfind `supercover()` hardening (`PolygonalMap2`) | **Yes** |
| Deferred/incremental cell unload queue (`ServerMap`) | No |
| Budgeted multi-tick load finalize (`ServerMap`) | No |
| Zombie no-cull baseline fix (`ZombieCountOptimiser`) | No |
| Zombie network auth tiering (`NetworkZombiePacker`) | No |
| Player LOS / FOW instrumentation and throttling (`ServerLOS`) | No |
| `ApocBRServerTelemetry` (any telemetry at all) | No |
| Lock-contention / chunk save-vs-load guard (`PlayerDownloadServer`) | No |
| Stale-chunk pathfind guard (`PathfindNative`, `ChunkUpdateTask`) | No |
| Entity/engine framework concurrency hardening (`EngineEntityManager` et al.) | No |

42.20.0 currently ships two small, low-risk, self-contained hardening/tiering fixes and

the two ported fixes are in fact the correct shape of "easy win": narrow, mechanical, no
threading model change, no interaction with the load/unload/LOS pipeline.

## 2. What 42.19.0 actually shipped, and what it taught us

`42.19.0/src` (31 files) implements a much larger surface area than what has been ported.
The `42.19.0/issues/` folder is a detailed post-mortem of that larger effort, and it is the
single most useful input for planning 42.20.0 because it documents not just what was built,
but what broke and why. Read together, `42.19.0/issues/` describes three generations of
work:

1. **Generation 1 - aggressive async/deferred rework.** Deferred unload queue with 60s
   grace, budgeted multi-tick load finalize, animal/zombie simulation tiering, zombie
   network auth tiering, broad telemetry.
2. **Generation 2 - production incidents caused by generation 1.** Server hangs from
   save/load lock contention (`HANG-ANALYSIS.md`, `LOCK-CONTENTION-FIX.md`,
   `CLIENT-RETRY-ANALYSIS.md`), and a black-building visual corruption bug from two
   independent LOS races introduced by the deferred unload/load pipeline
   (`PATCHED-SOURCE-DIFF-AUDIT-2026-07.md` Finding 1, `LOAD-FINALIZE-CELL-BOUNDARY-RACE-FIX-SCOPE.md`).
3. **Generation 3 - the "first stable release."** `FIRST-RELEASE-SERVER-OPTIMIZATIONS-OVERVIEW.md`
   describes a deliberate pull-back: keep the smoothing/telemetry, keep proven safety
   fixes, but explicitly avoid off-thread world mutation, async cell publish/commit, and
   off-thread Lua ownership changes, because those are what caused generation 2's incidents.

**The operative lesson for 42.20.0:** the deferred-unload + budgeted-load-finalize pattern
is valuable (it measurably reduces hitching - see `PERFORMANCE-ANALYSIS-2026-06-17.md`,
`serverMapPost` dropped from 267ms avg to 12ms avg), but it is **not safe to port in
isolation**. It shipped bugs in 42.19 precisely because of two things it changed implicitly:
how long a cell can sit "data-present-but-not-published" (load side) and "still-mutating-
while-marked-unloading" (unload side), both of which raced against `ServerLOS`'s single
atomic 96x96xZ scan thread. Porting the queue/budget mechanism to 42.20.0 without also
porting (or re-deriving, since `ServerLOS.java` is byte-identical between 42.19 and 42.20
decompiled - see section 3) the corresponding LOS-safety fixes would reintroduce the same
black-building class of bug on 42.20.0.

### 2.1 Confirmed bugs in 42.19.0/src that must NOT be blindly re-introduced

From `PATCHED-SOURCE-DIFF-AUDIT-2026-07.md`:

- **Finding 1 (critical):** `ServerMap.processDeferredUnloads()`'s per-tick partial unload
  never wraps itself in `ServerLOS.instance.suspend()/resume()`, unlike the load-finalize
  path. This is the leading root-cause candidate for the "building interior stays
  permanently black" report. If the deferred-unload queue is ever ported to 42.20.0, this
  suspend/resume wrapping must be added from day one, not retrofitted after a report.
- **Finding 2 (one-line, no design question):** `BodyDamage.java` compares
  `player.getAccessLevel() == "admin"` by reference instead of `.equals()`, silently
  defeating a godmode anti-cheat gate for real admin accounts. Safe, trivial, high-value
  fix, and worth carrying over even though it is not a "performance" fix.
- **Finding 3:** `ServerLOS.suspend()`'s `SUSPEND_WAIT_TIMEOUT_MS = 500L` early-exit can fire
  mid-scan under load, letting the load-finalize path mutate `IsoChunk.chunks[][]`
  concurrently with `calcLOS()`. This compounds Finding 1 and is only a "true safety net"
  once `SERVERLOS-SCALABILITY-TILE-SCAN-THROTTLE.md`'s Layer 1 (abandon-on-interrupt
  `calcLOS`, see section 2.3) is implemented.
- **Finding 6:** `AsyncLuaManager` / `ApocBRMainThreadLuaQueue` / the commented-out
  `IsoAnimal.update()` async override are unfinished, partially-dead scaffolding. The
  queue's `drain()` is never called from anywhere. **Do not port this into 42.20.0** in its
  current form; either finish it (wire `drain()` into the main loop and re-enable the
  animal override) or leave it out entirely. Given the "avoid big structural changes
  before telemetry" constraint, leaving it out is the correct call for now.
- **Finding 4 (low severity):** `IsoZombieGiblets.update()` spawns a new
  `CompletableFuture` every frame per instance with no single-flight guard, unlike the
  (disabled) `IsoAnimal` pattern that used `AtomicBoolean asyncUpdateInFlight`. Cosmetic/
  short-lived objects, so low priority, but cheap to fix correctly if async giblets are
  ever ported.

From `HANG-ANALYSIS.md` / `LOCK-CONTENTION-FIX.md` / `CLIENT-RETRY-ANALYSIS.md` (all three
describe the same incident from different angles - read `LOCK-CONTENTION-FIX.md` first,
it is the clearest single summary):

- The deferred unload queue (60s grace, multiple cells unloading concurrently) turned a
  vanilla-rare race - main thread `SafeRead()` blocking on a `ReentrantReadWriteLock` held
  by `SaveChunkThread`'s `SafeWrite()` during slow I/O - into a frequent one, because up to
  19 cells (1,216 chunks) could be mid-save simultaneously instead of vanilla's rare,
  atomic, single-cell-at-a-time unload burst.
- Confirmed client-side auto-retry exists already (`WorldStreamer.java` 8-second timeout
  re-queues the chunk request), so the fix that shipped (`APPLIED-FIXES.md`) was simply to
  check `hasPendingOrRunningSave(wx, wy)` in `PlayerDownloadServer` before calling
  `SafeRead()`, and `continue` (skip) if a save is in flight, relying on the client to
  retry in ~8s. This is safe, small, and **has no dependency on the deferred-unload queue
  existing** - it is good practice any time chunk saves and chunk reads can overlap at all,
  which is already possible in vanilla (just rare).
- Also shipped: increased `UNLOAD_SLICES_*`/`UNLOAD_CELLS_*` drain-rate constants to keep
  the unload queue from falling behind exploration pressure (`APPLIED-FIXES.md` Fix 1).
  `HANG-ANALYSIS.md` additionally proposes (documented, **not confirmed applied** per its
  own "Not Yet Applied" section) a bounded save queue with backpressure and a
  `SaveChunkThread` watchdog - these are still open recommendations even for 42.19.0, not
  settled solutions.

From `LOAD-FINALIZE-CELL-BOUNDARY-RACE-FIX-SCOPE.md` (status: **OPEN**, not yet fixed even
in 42.19.0): a second, independent LOS race caused by the *load*-side budgeted finalize
(`ServerCell.Load2()`/`RecalcAll2()` spread across multiple ticks instead of vanilla's
unconditional same-tick full drain). A cell's boundary-reconciliation pass treats a
neighbor cell with in-memory-but-unfinalized chunk data as "not there," silently skipping
cross-boundary LOS/pathfind linkage, which can then get permanently latched by
`ServerLOS`'s tile-change-skip optimization. This is a **second distinct mechanism** from
Finding 1, not a duplicate - do not treat fixing one as covering the other. The fix scoping
document is detailed and actionable (`Option 1`: boundary-aware getter that bypasses the
`isLoaded` gate for the reconciliation pass; `Option 2`: force LOS resample near
just-finalized cells as a safety net) but was never marked implemented/closed.

From `moving-object-scheduler-double-postupdate.md`: a bug where `IsoCell.update()` (42.19
patched) called `MovingObjectUpdateScheduler.instance.postupdate()` once, and
`IsoWorld.updateWorld()` called it again immediately after, doubling post-update work per
frame. The report notes this is **mostly harmless on the dedicated server specifically**
(server always uses `FULL`/fixed per-object multiplier, so no time-acceleration effect),
but it is real waste and a client-side correctness bug (3-4x apparent zombie/entity speed
locally). If `IsoCell`/`IsoWorld` update-loop restructuring is ever revisited, this is a
concrete regression to check for, not a pattern to copy.

### 2.2 What worked and is safe to consider porting on its own merits

- **Vehicle/animal simulation tiering** - already ported (section 1.1). No further action
  needed beyond adding telemetry counters once the telemetry pack exists.
- **`supercover()` hardening** - already ported (section 1.3). No further action needed.
- **Zombie no-cull baseline fix** (`ZombieCountOptimiser.deleteZombies()` disabled) -
  simple, well-isolated, addresses a real vanilla-multiplayer complaint (server
  over-deleting zombies under load, making the world feel empty). No load/unload/LOS
  interaction. Good easy-win candidate.
- **Godmode `.equals()` fix** (`BodyDamage.java`) - one-line, no design questions, no
  performance angle but zero risk and closes an anti-cheat hole. Good easy-win candidate
  regardless of the optimization focus of this report.
- **Anti-cheat `ExtraInfoPacket` admin gate** - per the audit, already correct
  (`hasAdminPower()`), so this is a "verify it holds in 42.20" item, not new work.
- **Increased unload drain-rate constants alone, without the deferred-queue/60s-grace
  mechanism** - i.e., taking the numeric tuning idea (drain more aggressively once a queue
  exists) is meaningless without the queue; this only applies *if and when* the deferred
  unload queue is ported. Do not apply drain-rate tuning without the mechanism it tunes.
- **Bounded, per-square teardown work and lock-contention avoidance in
  `PlayerDownloadServer`** - these are only relevant once/if a deferred unload queue is
  ported, since vanilla's atomic single-cell unload does not create the concurrent-save
  pressure that motivated them.

### 2.3 What worked but is NOT safe to port yet (needs its own prerequisite work first)

- **Deferred/incremental cell unload queue** and **budgeted multi-tick load finalize** -
  the single biggest frame-pacing win in 42.19.0 (`serverMapPost` 267ms -> 12ms avg per
  `PERFORMANCE-ANALYSIS-2026-06-17.md`), but shipped two confirmed/suspected LOS races
  (Finding 1, and the open `LOAD-FINALIZE-CELL-BOUNDARY-RACE-FIX-SCOPE.md`) and one
  confirmed production hang class (lock contention, `HANG-ANALYSIS.md`). Porting this to
  42.20.0 is explicitly a **deep structural change** and should wait until: (a) the
  telemetry pack in section 4 is live and has established a healthy baseline, and (b) this
  report's Finding-1-equivalent fix and the `PlayerDownloadServer` save/load guard are
  planned as part of the same change, not follow-ups.
- **`SERVERLOS-SCALABILITY-TILE-SCAN-THROTTLE.md`'s Layer 1/Layer 2** - a well-specified,
  self-contained plan to make `calcLOS()` interruptible (abandon-on-interrupt with a
  `pendingVisible` buffer swap) and to rate-limit per-player tile scans under load. This is
  independently valuable (it is what turns Finding 3's 500ms timeout from "routinely-hit
  escape hatch" into "true safety net") and does **not** depend on the deferred-unload
  queue existing - `ServerLOS.java` is byte-identical between 42.19 and 42.20 decompiled
  (see section 3), so this plan applies to 42.20.0 unchanged. It is more surgical than the
  unload/load queue work and does not touch `ServerMap`'s publish/commit ownership model at
  all - it only changes how the LOS thread schedules and interrupts its own scan. Good
  candidate for "next tier after telemetry," ahead of the full deferred-unload port.
- **Async unload / async world mutation in general** - `async-unload-analisys.md`
  identifies 5 high-risk and 2 medium-risk static-field/singleton mutation points
  (`RainManager`, `IsoWorld.currentCell` survivor list, `MapCollisionData`,
  `PathfindNative`/`PolygonalMap2`, `AnimalPopulationManager.newChunks`,
  `ZombiePopulationManager`) that would need synchronization before any full async unload
  could be safe, and its own conclusion recommends **against** full async unload as
  anything but a last resort. This aligns with the user's stated constraint to avoid deep
  structural change for now; treat this document as a reason to *not* pursue async unload,
  not a blueprint to implement it.
- **`SERVERCELL-LOAD-COMMIT-REPORT.md`'s worker-side commit experiment** - explicitly
  described as an experiment design, not a shipped fix, with its own required-invariants
  and validation-matrix sections still open. Same category as async unload: valuable
  research, not a near-term port target.

## 3. Vanilla drift between 42.19 and 42.20 (porting-risk assessment)

Before porting anything from `42.19.0/src`, it matters whether the *vanilla* base classes
those patches touch have changed shape between build 42.19 and 42.20. Diffed
`42.19.0/decompiled` against `42.20.0/decompiled` directly:

| File | Vanilla drift 42.19 -> 42.20 | Porting-risk implication |
|---|---|---|
| `zombie/network/ServerLOS.java` | **Identical, zero diff** | Any 42.19 `ServerLOS` fix (Finding 3, the tile-scan-throttle plan) applies to 42.20 with no adaptation needed. |
| `zombie/network/ServerMap.java` | +6 lines only | The core `Load2()`/`Unload()`/`preupdate()`/`postupdate()` structure is stable; the deferred-unload/budgeted-finalize port should be low-adaptation-effort *mechanically*, though still high-risk for the LOS-race reasons in section 2.3. |
| `zombie/network/PlayerDownloadServer.java` | ~21 lines changed | Small drift; the `SafeRead()`/save-check guard from `LOCK-CONTENTION-FIX.md` should port with minor adjustment. |
| `zombie/iso/IsoCell.java` | ~121 lines changed | Moderate drift. Re-verify `ProcessObjects`/`ProcessStaticUpdaters`/`ObjectDeletionAddition` ordering and the `postupdate()` call site against 42.20 before reapplying any `IsoCell` changes, to avoid reintroducing the double-`postupdate()` bug from `moving-object-scheduler-double-postupdate.md`. |
| `zombie/iso/IsoWorld.java` | ~213 lines changed | Largest drift among world-loop files. Any port of the parallel `updateThreadSafeParallel()`/`updateThreadMainOnly()` split needs a fresh read of 42.20's `updateInternal()`, not a blind diff-apply. |
| `zombie/iso/IsoChunk.java` | ~221 lines changed | Largest drift overall. `removeSquareFromWorld()`, `SafeRead`/`SafeWrite`, and the `ChunkLock` implementation should be re-read in 42.20 before reapplying any unload-path or lock-contention fix; line numbers cited in the 42.19 issue docs will not match. |
| `zombie/network/GameServer.java` | ~240 lines changed, but changes are concentrated in faction/helmet-fall/misc packet-handling removals and `networkAi` -> `getNetworkCharacterAI()` API renames | The main server loop shape (`startServerCycle`, `MainLoopNetDataHighPriorityQ`/`MainLoopPlayerUpdateQ`/`MainLoopNetDataQ` polling, `ServerMap.instance.preupdate()/postupdate()` call sites, `Players`/`getZombieList()`) is intact and at the same structural position - confirmed by direct inspection of `42.20.0/decompiled/zombie/network/GameServer.java` lines 843-1157. Telemetry hook points described in section 4 are valid against 42.20 vanilla as-is. |

**Practical takeaway:** `ServerLOS`-focused work (Finding 3 fix, tile-scan-throttle plan) is
the lowest-adaptation-risk carryover from 42.19.0 because the file hasn't changed at all.
`ServerMap`/`PlayerDownloadServer` changes are next-lowest risk. `IsoCell`/`IsoWorld`/
`IsoChunk` changes need the most re-verification against current 42.20 line-for-line
content before reapplying, since naive patch/diff application against those three files is
likely to fail or subtly misapply.

## 4. Telemetry plan for 42.20.0

There is currently **zero telemetry** in `42.20.0/src`. This is the top-priority item:
every other optimization decision in this report ("is the unload queue keeping up," "is LOS
the bottleneck," "is zombie count the limiting factor") was only knowable in 42.19.0
*because* `ApocBRServerTelemetry` existed. Per the user's request, this pass should ship a
**smaller, focused** telemetry pack, not the full 42.19.0 surface - the 42.19.0 class grew
to instrument dozens of subsystems, most of which do not exist in 42.20.0 yet (deferred
unload, LOS throttling, zombie network tiering, etc.). Build only what 42.20.0 needs today.

### 4.1 Required metrics (from the request)

- **Players online** - already trivially available as `GameServer.Players.size()`.
- **Zombies** - available as `IsoWorld.instance.currentCell.getZombieList().size()`, same
  source 42.19.0 used (`recordQueueSnapshot`'s `zombies` parameter).
- **Server loop frame rate** - the server main loop is fixed-step at a 10 FPS design
  target (confirmed by the user; also consistent with 42.19.0's `world.ticks` metric using
  a 30-second window where a fully healthy server should log **~300 ticks** per snapshot).
  Count ticks in the snapshot window and report both the raw tick count and the derived
  average tick duration (`avgMs`)/`maxMs` for the worst tick in the window - `avgMs` alone
  hides single-frame hitches that a max-tracking field will catch.
- **Packet queue depth** - the three main-loop queues already exist in vanilla
  `GameServer`: `MainLoopNetDataHighPriorityQ`, `MainLoopPlayerUpdateQ`, `MainLoopNetDataQ`.
  `.size()` on each is the queue depth at end-of-tick, exactly what 42.19.0's
  `recordQueueSnapshot(highQueue, playerQueue, normalQueue, connections, players, zombies)`
  captured.
- **30-second snapshot cadence, ~300-frame healthy baseline at 10 FPS** - matches the
  existing 42.19.0 `INTERVAL_MS` default of 30000ms; reuse that cadence and make it
  overridable via a system property the same way 42.19.0 did
  (`apocbr.telemetry.intervalMs`), so it can be tuned without a recompile.

### 4.2 Design: `ApocBRServerTelemetry` (minimal, 42.20.0-scoped)

Model this closely on the *shape* of 42.19.0's class (static synchronized counters, a
`maybeLog()` gate, a JSON log line via `DebugLog.log(...)`) but with only the fields
described above - do not carry over sections for subsystems 42.20.0 doesn't have yet
(unload queue, load finalize, zombie network breakdown, LOS, moving-object buckets, vehicle
Lua). Adding those sections should happen alongside porting the corresponding optimization,
not ahead of it - an empty/always-zero telemetry section is worse than no section, because
it looks like a healthy signal.

Proposed minimal field set:

```
{
  "ts": <epoch ms>,
  "windowMs": <actual elapsed ms since last log>,
  "world": {
    "ticks": <count in window>,
    "avgMs": <avg tick duration>,
    "maxMs": <worst tick duration in window>
  },
  "state": {
    "players": <Players.size() at last tick>,
    "zombies": <currentCell.getZombieList().size() at last tick>
  },
  "queues": {
    "high": <MainLoopNetDataHighPriorityQ.size()>,
    "player": <MainLoopPlayerUpdateQ.size()>,
    "normal": <MainLoopNetDataQ.size()>,
    "connections": <udpEngine.connections.size()>
  }
}
```

At 10 FPS and a healthy 30s window, `world.ticks` should read **~300**. A number
meaningfully below 300 is the single clearest "the server is not keeping up" signal
available without any subsystem-specific instrumentation - this is intentional, since the
whole point of a minimal first pass is "detect that something is wrong" before "diagnose
what."

### 4.3 Implementation hook points (verified against 42.20.0 decompiled)

All hook points below were confirmed present and at a stable position in
`42.20.0/decompiled/zombie/network/GameServer.java`:

- **Tick timing:** wrap the existing per-cycle work with `System.nanoTime()` at the top of
  the `while (!done) { ... }` loop (`startServerCycle`, line ~846) and record the delta once
  per iteration, mirroring how 42.19.0 called `recordWorldTick(System.nanoTime() -
  startServerCycle)` at the end of its loop body.
- **Player/zombie/queue snapshot:** call once per tick, near the same place 42.19.0 did (end
  of the frame body, after `ServerMap.instance.postupdate()` at line ~1086), reading
  `Players.size()`, `IsoWorld.instance.currentCell.getZombieList().size()`,
  `MainLoopNetDataHighPriorityQ.size()`, `MainLoopPlayerUpdateQ.size()`,
  `MainLoopNetDataQ.size()`, and `udpEngine.connections.size()`. Guard the zombie/cell reads
  with the same null checks 42.19.0 used
  (`IsoWorld.instance != null && IsoWorld.instance.currentCell != null`).
- **Log gate:** call `ApocBRServerTelemetry.maybeLog()` once per tick, after the snapshot
  call, exactly like 42.19.0's placement.

This requires touching exactly one vanilla file (`GameServer.java`) plus adding one new
file (`ApocBRServerTelemetry.java`). It does not touch `ServerMap`, `IsoCell`, `IsoWorld`,
or `IsoChunk`, so it carries none of the porting risk flagged in section 3 for those files.
This should be implementable and safe to ship immediately, ahead of any of the "easy win"
items in section 5, since every later decision in this plan depends on having this data.

### 4.4 Note on packet queue interpretation

A queue depth of 0 at end-of-tick is normal and healthy - the queues are drained every
tick by design (see the `MainLoopNetDataHighPriorityQ.poll()`/`MainLoopPlayerUpdateQ.poll()`/
`MainLoopNetDataQ.poll()` loops in `GameServer`). A **non-zero, growing** queue depth
sampled consistently across snapshots is the actionable signal - it means packet intake is
outpacing per-tick drain, which at a 70-slot server would most likely show up first in
`player` (unreliable/reliable player-update packets) under a sudden burst (e.g., many
players reconnecting or a network hiccup), not gradually. Treat any sustained non-zero
value here as worth investigating before treating it as an optimization target.

## 5. Recommended order of work for 42.20.0

Given the constraints (70-slot server currently healthy, no telemetry, avoid deep
structural change before telemetry exists, prioritize player-action responsiveness and
chunk loading), the recommended sequence is:

### Phase 0 - Telemetry (do first, blocks informed decisions on everything else)

1. Ship the minimal `ApocBRServerTelemetry` from section 4. This is the single highest-
   leverage item: it turns every subsequent decision from a guess into a measurement, which
   is exactly the gap 42.19.0's own history shows matters (compare `PERFORMANCE-ANALYSIS-2026-06-17.md`,
   which was only possible because telemetry already existed, against 42.19.0's *earlier*
   undocumented hang, which had to be diagnosed after the fact from vague symptom reports).

### Phase 1 - Easy wins (no threading model change, no load/unload/LOS interaction)

These match the "easy win" bar the user set: narrow, mechanical, isolated, and consistent
with what has already been ported to 42.20.0 in the same spirit.

2. **Godmode `.equals()` anti-cheat fix** (`BodyDamage.java`, Finding 2) - one line,
   zero risk, closes a real hole.
3. **Zombie no-cull baseline fix** - re-verify `ZombieCountOptimiser.deleteZombies()`'s
   current 42.20 vanilla behavior first (it may differ from 42.19's), then decide whether
   the same disable is still warranted. Low complexity, self-contained, directly relevant
   to "responsiveness for player actions" since it affects how much of the world's zombie
   population the server has to carry, without touching the update-scheduling code already
   ported in section 1.1.
4. **Wire telemetry counters into the two already-ported files** (`MovingObjectUpdateScheduler`'s
   vehicle/animal tiering, `PolygonalMap2`'s `supercover()` guard trip count) once Phase 0
   lands, so their real-world effect becomes visible instead of assumed.
5. **`IsoZombieGiblets.update()` single-flight guard** (Finding 4) - only relevant if/when
   giblets are made async on the server; otherwise no action needed since the server-side
   giblet path today is presumably still synchronous vanilla behavior (verify before
   treating this as applicable to 42.20.0 at all).

### Phase 2 - LOS scalability (self-contained, zero drift risk, no `ServerMap`/`IsoCell` involvement)

6. Implement `SERVERLOS-SCALABILITY-TILE-SCAN-THROTTLE.md` Layer 1 (abandon-on-interrupt
   `calcLOS` via `pendingVisible` buffer swap) against 42.20.0's `ServerLOS.java`, which is
   byte-identical to 42.19's per section 3 - this plan can be implemented essentially
   as-written. This directly targets "responsiveness for player actions," since
   `serverMapPreMaxMs` (main thread blocked waiting for LOS to yield) was measured at
   150ms at only 22 players in 42.19.0, and would only get worse at 70 slots without this
   fix.
7. Layer 2 (per-player tile LOS interval / rate-limiting) as a follow-up once Layer 1's
   telemetry (`playerLOSAbandoned`, `playerLOSTileSkipped`) confirms Layer 1 is behaving as
   expected under real load.

This phase requires adding the LOS-specific telemetry fields described in
`SERVERLOS-SCALABILITY-TILE-SCAN-THROTTLE.md` section "Telemetry Additions" to the
minimal telemetry class from Phase 0 - this is the first subsystem-specific extension,
and it should only be added once the LOS work itself is being implemented (per section
4.2's guidance against speculative always-zero fields).

### Phase 3 - Deferred unload / budgeted load finalize (deep structural change - gate behind telemetry data)

8. **Do not start this phase until Phase 0's telemetry has run in production long enough to
   establish what "healthy" looks like on the 70-slot server**, per the user's explicit
   constraint. When it is time:
   - Port the deferred-unload queue and budgeted load-finalize together, not separately.
   - Include the Finding-1 fix (`ServerLOS.instance.suspend()/resume()` around each
     `processDeferredUnloads()` unload slice) as part of the same change, not a follow-up -
     shipping the queue without this fix is exactly how 42.19.0 got its black-building bug.
   - Include the `LOAD-FINALIZE-CELL-BOUNDARY-RACE-FIX-SCOPE.md` Option 1 fix (boundary-
     aware getter bypassing `isLoaded` for the reconciliation pass) in the same change,
     since it addresses the load-side counterpart of the same race family.
   - Include the `PlayerDownloadServer` save-in-progress guard
     (`hasPendingOrRunningSave()` check before `SafeRead()`) proactively, not reactively -
     42.19.0 only added it after a production hang; there's no reason to wait for a repeat
     on 42.20.0.
   - Re-derive line numbers and surrounding code fresh against 42.20.0's `ServerMap.java`,
     `IsoChunk.java`, and `PlayerDownloadServer.java` - do not attempt to mechanically
     replay the 42.19.0 diffs, since (per section 3) `IsoChunk.java` in particular has
     ~221 lines of unrelated vanilla drift.
   - This is the change most directly responsible for "good chunk loading" in the original
     42.19.0 data (`serverMapPost` 267ms -> 12ms avg), so it remains the highest-value
     structural change once the prerequisites above are satisfied - it is just not a
     Phase-1 "easy win."

### Explicitly deferred / not recommended for 42.20.0 right now

- Async cell unload / async world mutation (`async-unload-analisys.md`'s own conclusion).
- The async Lua queue and animal-async scaffolding (Finding 6) - finish or delete, don't
  carry forward half-wired.
- The worker-side cell-commit experiment (`SERVERCELL-LOAD-COMMIT-REPORT.md`) - research
  document, not a port target.
- Any `IsoWorld`/`IsoCell` update-loop parallelism restructuring - highest vanilla drift
  (section 3) and the source of a confirmed correctness bug in 42.19.0
  (`moving-object-scheduler-double-postupdate.md`). Revisit only after Phase 3 stabilizes
  and only with fresh 42.20.0-specific analysis.

## 6. Summary

- 42.20.0 today has two small, correctly-scoped, low-risk ports from 42.19.0 (vehicle/
  animal server simulation tiering, `supercover()` hardening) plus one unrelated container-
  capacity balance change. This is a good foundation, not a false start.
- 42.19.0's larger body of work is valuable but came with two confirmed LOS-race bug
  classes and one confirmed production hang, all caused by the same underlying change (the
  deferred-unload/budgeted-load-finalize pipeline) shipping without complete concurrency
  safety around `ServerLOS`. Do not port that pipeline piecemeal or without its safety
  fixes.
- `ServerLOS.java` is unchanged between 42.19 and 42.20 vanilla, making the LOS-scalability
  plan the best "next tier" structural work: self-contained, well-specified, and directly
  addresses responsiveness at higher player counts without touching the unload/load
  ownership model at all.
- `IsoCell.java`, `IsoWorld.java`, and `IsoChunk.java` have the most vanilla drift and
  should be treated as "re-derive against current 42.20 source," not "reapply the 42.19
  diff," whenever their turn comes.
- The immediate next action is the minimal telemetry pack in section 4 - players, zombies,
  tick rate (expect ~300 ticks/30s at a healthy 10 FPS), and the three packet queue depths -
  since every prioritization decision after that point should be backed by data from the
  actual 70-slot server rather than by 42.19.0's numbers, which were captured under
  different code and different load.
