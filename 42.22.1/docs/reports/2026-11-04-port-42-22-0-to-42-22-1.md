# 42.22.0 to 42.22.1: vanilla changes and patch carry-forward

Date: 2026-11-04. Target: unsuffixed dedicated-server patch tree.

## Decision

**Proceed with a small, controlled carry-forward. Do not copy every file blindly.**
The entire supplied vanilla comparison contains only four modified Java files,
one added Java file and no removals. Of the current **305** patch sources, **304
can retain their implementation** at this source-compatibility stage. The remaining
file, `GameServer.java`, needs a clean, two-hunk upstream merge to preserve the
42.22.1 integrity-report startup and revision logging. Build-label metadata in
three custom sources also requires an explicit compatibility decision before
calling the result a correctly identified 42.22.1 persistence target.

A temporary candidate containing all current sources plus that GameServer merge
compiled successfully against the installed target JAR: **305 Java sources,
902 class files, javac 25.0.4, exit 0**. Nothing was deployed or copied into a new
`42.22.1/src` tree. This report fulfills the audit; it is not a completed port or
a claim of runtime validation.

## Integrity behavior that affects our installation

The added [IntegrityReport](../../decompiled/zombie/core/IntegrityReport.java)
locates the JAR containing itself and reads its non-signature entries with Java
JAR verification enabled. It reports unreadable/missing/modified/unsigned entries
and signers whose certificate fingerprint does not match its pinned fingerprint.
It scans other Java classpath entries: directories recursively contribute loose
`.class` paths, while other entries are recorded directly. It also records JVM
agent arguments and an `Attach Listener` thread when present.

Consequently our loose-class deployment and extra dependency JARs can contribute
to `classpath=N` in the version diagnostic even when the original game JAR is
untouched. That number is the number of findings, not necessarily the number of
our overridden classes. The classpath scan is not limited to `zombie/`.

The supplied implementation does **not** directly hash the installed JRE image.
Its visible checks concern the game JAR, classpath, agents and attachment state;
additional JRE-related changes may exist outside this source snapshot. No shutdown,
connection rejection or enforcement call is visible in the report or its callers
in this tree. Its observed consumers are Core version text and startup/version
output. That source observation does not guarantee publisher policy or behavior
outside the inspected code. Preserve the upstream checker and its diagnostics.

Copying the old patched GameServer unchanged would still compile because the new
call is additive. It would omit server collection startup; absent another caller,
Core's version text would remain `integrity=pending`. Compilation alone therefore
misses a real behavior difference.

The local backend's
[V34 migration](../../../../apocalipsebr-manager/manager/src/main/resources/db/game-runtime-migration/V34__Support_42_22_World_Dictionary_Namespaces.sql)
allows only `(42.21.0,249)` and `(42.22.0,251)` for dictionary namespace metadata.
Searching that local migration directory found no 42.22.1 allowance. A new backend
migration must admit `(42.22.1,251)` **before** publishing under that build label;
do not edit an already-applied migration or relabel historical namespaces. Live
database state was not queried. If exact-build namespaces remain the policy, extend
the existing supported-previous-build rollover to 42.22.0 as well as historical
reads. Keeping the old labels avoids that new constraint failure but misidentifies
new data; it is not a completed metadata migration.

The [42.22.0 historical dictionary guide](../../../42.22.0/docs/features/2026-10-29-historical-dictionary-compatibility.md)
owns that persistence contract. Its provenance and namespace isolation remain
applicable even though world format did not change.

## Recommended execution order

1. Carry forward the current sources, libraries and required tools/scripts into
   42.22.1, preserving 42.22.0 as history. Apply the attached GameServer diff.
2. Coordinate build labels, dictionary pair acceptance, historical reads and any
   namespace rollover with a new backend migration. Preserve source history.
3. Update target script/manifests/docs references. Select the latest version only
   once its build entry point exists; a higher-numbered vanilla directory alone
   does not make a usable patch target. No Git branch was created by this audit.
4. Run the target dry build and focused dictionary publication/read/rollover
   fixtures for the new pair, including restart/reuse and historical payload reads.
5. On a disposable world/database copy, verify startup/version diagnostics, login,
   inventory reconstruction/save/reconnect, NPC combat/trading, vehicle physics,
   streaming and shutdown. Resolve inherited stale-class cleanup before deployment.

Existing reconstruction coverage gaps, concurrency limitations and deployment
cleanup debt are inherited from the current implementation; this minor update
does not resolve them. No new gameplay rebase is indicated by the supplied source.
