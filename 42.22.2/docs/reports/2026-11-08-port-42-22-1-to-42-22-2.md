# 42.22.1 to 42.22.2: initial compatibility and porting report

Date: **2026-11-08**. Target: **42.22.2 server patches**. Status: **audit complete;
port not applied**. Client initialization changes are included in the vanilla
comparison, but separate client patch directories were not audited.

## Finding

This is a small source port from the current 42.22.1 implementation. Only five
supplied vanilla Java files changed. Four concern version/revision identification;
the substantive change removes attachment detection from `IntegrityReport`.
Only **GameServer** intersects our replacement classes, and its upstream delta
is two revision string literals. No gameplay rebase, replacement retirement or
custom-class collision is indicated by the supplied sources.

A temporary copy of all **339 current working-tree sources**, with those two
GameServer literals updated, compiled against the installed 42.22.2 original
`projectzomboid.jar`: **javac 25.0.4, exit 0, 984 class files**. This establishes
source/API compatibility for that candidate, not runtime readiness.

The user's supplied changelog describes a Windows false-positive `attached`
diagnostic fix. The local source confirms a broader implementation detail:
attachment detection is removed unconditionally, with no Windows-only branch.
The publisher changelog was supplied as context, not independently verified here.

## Exact integrity fix and operational implications

42.22.1 queried `ThreadMXBean`, looking for an `Attach Listener` thread, recorded
`Problem.ATTACHED`, and appended `attached` to the summary. 42.22.2 removes:

- The `ThreadInfo`/`ThreadMXBean` imports and listener-name constant.
- Calls to `findAttached()` in both report constructors.
- `findAttached()` and `isAttached()` themselves.
- The summary branch and the `Problem.ATTACHED` enum entry.

JAR verification, pinned signer fingerprint, classpath scanning, JVM agent
argument scanning, background collection and publication remain unchanged.
Removing `attached` therefore does not clear unsigned-JAR, extra-classpath or
agent findings. No reference to the removed enum entry exists in our 339 sources.
The only custom IntegrityReport references are GameServer's import/startup call.

Carry forward the existing
[unsigned runtime deployment implementation](../../../42.22.1/docs/features/2026-11-04-unsigned-runtime-deployment.md).
This update does not remove Java's signed/unsigned package compatibility issue.
The helpers must derive the managed runtime from the **new original JAR** and
refresh its hash receipt after the game update. Do not reuse an old derived JAR
as the new build input. Preserve the original JAR and upstream diagnostics.
The active IDE launcher JSON and installed runtime were not modified by this audit.

## Candidate build evidence and limits

The candidate was created in a temporary directory from current 42.22.1 `src/`.
Only two occurrences of `71e8410c42` in GameServer were changed to `3d39148846`.
Every Java source was explicitly passed to the compiler using an argument file:

```text
javac --release 25 -Xlint:none -implicit:none -encoding UTF-8
      -cp <original target JAR;HikariCP-7.1.0.jar;postgresql-42.7.14.jar>
      -sourcepath <temporary src> -d <temporary classes> <all 339 Java files>
```

Installed original:
`Z:/SteamLibrary/steamapps/common/ProjectZomboid/projectzomboid.jar`.
SHA-256: `3c4a7c5f149d784758c6fb5f8fa85f3a21d572e38bc081400e89035f8120d287`.
`javap` confirmed revision **3d39148846** and world **251**. Dependency hashes,
compiler options and candidate GameServer hash are in the build receipt.
The compiler emitted only deprecated/unchecked-operation notes.

Temporary source/classes were removed on completion. No deployable target ZIP
was retained, and no 42.22.2 `src/` or patch entry point was installed. No game
initialization, native library execution, database access, gameplay fixture or
server startup was performed. Compilation does not validate runtime ownership,
SQL constraints, reconstruction fidelity, launcher execution or networking.
